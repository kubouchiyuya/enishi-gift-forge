# Reference Review and Improvement Log

参照元: Grok共有URL（ログイン済みIn-app Browserで本文確認済み）
対象テーマ: 「発信者から、事業者へ。SNS発信者向け協業セミナー」

## 参照元の良かった点

- プレゼントを単なる資料ではなく、スキル＋プロンプトの実用品として捉えた
- インスタグラマー、経営者、AI中級者を対象にした
- 発信→商品化→コミュニティ・協業という流れを作った
- 5分で開始できる導線、Notion/PDF、7日間の実践を提案した
- 商品化ワークシート、協業提案書、ヒアリングシートを組み合わせた

## 問題点と改善

| ID | 問題 | 改善 |
|---|---|---|
| R01 | セミナー情報がログイン制で確認できず、初期提案が一般論になった | 対象者・目的・テーマを入力契約にし、未確認は`[TBD]`にする |
| R02 | 「一番」「全員に刺さる」「参加率が上がる」など成果を断定した | 仮説・検証方法・観測指標に変換する |
| R03 | GitHubのスター数・Trendingを根拠として提示した | 取得日時、URL、定義、分母を必須化し、未確認数値は禁止 |
| R04 | `last30days-skill`、`agent-skills`、`i-have-adhd`の導入を直接勧めた | 第三者資産は任意アダプター化し、Komainu・LICENSE・SHA・再スキャンを要求 |
| R05 | 3つの外部Skillを並べただけで、統合契約が弱い | ENISHI本体だけで発信→商品化→協業→検証を完結させる |
| R06 | `touch ~/.claude/...`のようなグローバル設定変更を案内した | プロジェクト内配置を標準にし、グローバル変更はしない |
| R07 | 価格・高単価・協業成果を根拠なく連想させた | 価格は仮説、実績は本人入力、PoCはPoCとして表示する |
| R08 | 「プロンプト集」が汎用品化する危険がある | 専門性・対象顧客・協業課題に紐づけた生成物だけを作る |
| R09 | 発信量を成果とみなす恐れがある | 相談、面談、試用、紹介、継続意思など事業シグナルを測る |
| R10 | 受け取った人の次の行動が曖昧 | 5分スタートと7日間スプリントを固定する |
| R11 | 外部送信やインストールの承認境界がない | 外部送信・購入・連携・インストールを承認必須にする |
| R12 | ソースのアイデアと自作部分の境界が曖昧 | Source Cardと独立設計の差分を公開記録に残す |

## 改善版の中心設計

```text
発信テーマ
  -> 専門性・根拠の棚卸し
  -> 対象顧客と課題の特定
  -> 商品コンセプト・価格仮説
  -> 協業提案・ヒアリング
  -> 少数の検証発信
  -> 7日間の継続/変更/中止判断
```
